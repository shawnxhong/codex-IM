## R1：追加输入没有“不确定”状态

位置：[sessions.py](../../src/codex_im/core/sessions.py)，166–183 行；[store.py](../../src/codex_im/core/store.py)，216–234 行。

`_try_steer()` 在 `await handle.steer(text)` 成功返回之后才把入站记录从 `queued` 改为 `steered`。任何异常都返回 False，让输入继续留在普通任务队列。

若 Codex 已接受并开始处理追加输入，但回复在断线时丢失，这个异常不能证明输入没有执行。流结束或转入恢复后，worker 会再次把这条 queued 消息交给 `start_turn()`。在成功追加后、写入状态前崩溃，也有同样的窗口。这违反 D14 的“可能已产生副作用的输入不自动重跑”。

建议：发送追加请求前持久化一次追加操作及其目标 turn；只对能证明未被接收的拒绝结果恢复 queued。传输中断、超时和崩溃窗口应进入待对账/unknown 状态，不自动重放。

Ubuntu 回归：模拟 `steer()` 先将输入记录到远端历史，再抛出 `TransportClosedError`；断线恢复后检查该输入没有被自动作为新 turn 执行。另覆盖追加操作前后的崩溃点。

## R2：已接收的 /new 不能阻止 worker 提前消费后续输入

位置：[sessions.py](../../src/codex_im/core/sessions.py)，163–164、186–201、204–238、573–594 行。

命令使用独立队列，但 `switch_pending` 只在命令 worker 真正执行 `/new` 时设置。若按顺序收到 `/stop`、`/new`、普通消息，命令 worker 会先等待 `/stop` 完成。旧 turn 的 worker 设置 idle 后，会立即继续检查普通队列；这时排在 `/stop` 后的 `/new` 可能尚未被执行。

存在普通消息先被旧 thread 接收、甚至在 `/new` 执行时又被中断的调度路径。这正是 V5-1 要避免的结果。现有 `test_new_during_turn_switches_thread_and_routes_followup` 只覆盖单独 `/new`，没有前置 `/stop`。

建议：在接收/排序命令时就建立切换屏障，或用统一的会话控制序列确保 worker 在消费后续消息前先应用已经收到的切换命令。不要只依赖命令 worker 何时获得调度。

Ubuntu 回归：用可控制完成时机的旧 turn，依次注入 `/stop`、`/new`、普通消息；在停止完成边界放行 worker，断言普通消息只提交给新 thread。

## R3：本地停止等待不代表远端停止执行

位置：[sessions.py](../../src/codex_im/core/sessions.py)，230–236、340–342、430–440、509–527、537–552 行；[app.py](../../src/codex_im/app.py)，81–86 行。

停止超时会取消本地消费任务；`_run_turn()` 的 finally 随即释放项目锁，worker 的 finally 把会话恢复为 idle。发生传输错误并安排 reconciliation 时，也走同样的释放路径。

只要旧 Codex turn 仍在执行，另一个会话就能拿到相同 serial 项目的锁并修改同一目录。原会话的新消息也可以再次调用 `thread.turn()`；该 SDK 接口允许加入仍活动的 turn，因此不能把它等同于“已开始一个全新的任务”。

启动恢复同样先后台安排 reconciliation，再立即 `kick_all_queued()`，没有用持久化的未完成任务恢复项目占用或阻止相同 thread 的新任务。

建议：将“本地消费者结束”和“远端执行已结束”分开管理。unknown/reconciling 的任务保留项目占用或把项目标记为待确认；只有确认远端终态后才放行。重启时先恢复这些约束。此处不能只依赖 `VERIFY(ubuntu)`，因为代码已经无条件释放互斥。

Ubuntu 回归：让远端 turn 忽略中断并继续运行，触发停止超时，同时从另一个会话向相同 serial 项目发任务；断言后者不会启动。对重启时存在 `inProgress` 历史的情况做同样检查。

## R4：停止超时没有覆盖控制 RPC

位置：[sessions.py](../../src/codex_im/core/sessions.py)，166–175、529–552、554–570 行。

`request_stop()` 先等待 `_interrupt(handle)`，返回后才进入使用 `stop_timeout` 的 `_wait_idle_or_abandon()`。如果连接未关闭但中断 RPC 不返回，停止超时根本不会开始计时，同一命令队列中的 `/status`、`/new` 也无法执行。

此外，`_try_steer()` 在持有 `rt.lock` 时等待网络请求。一条没有返回的追加 RPC 会让 `/stop` 连状态锁都拿不到。该标签 SDK 的 request 等待路径没有可由这些调用传入的超时参数。

建议：使用覆盖整个停止流程的截止时间；状态锁只用于检查和更新本地状态，把网络等待移出短锁。超时后按 R1/R3 的不确定状态处理，而不是假定取消了远端操作。

Ubuntu 回归：分别模拟永不返回的 `interrupt()` 和 `steer()`，验证停止流程能够在配置期限内给出状态，并且 `/status` 仍可响应。

## R5：outbox 顺序只在单次扫描内有效

位置：[outbox.py](../../src/codex_im/core/outbox.py)，71–79 行；[store.py](../../src/codex_im/core/store.py)，427–430 行。

`blocked` 每轮扫描都会重建，而 SQL 只查询已经到达 `next_attempt_at` 的记录。第一条投递失败后被推迟，下一轮扫描就看不到它，却能看到同会话尚未投递的第二条，第二条因此先发出去。

长回答的分段会乱序；澄清问题投递失败时，其后的最终回答也可能先到。单条消息失败后重试的现有测试无法发现这个问题。

建议：选择每个会话最早的 pending 记录作为投递屏障，不允许后续记录越过仍在退避中的前驱；前驱 sent/dead 后才继续。

Ubuntu 回归：同会话准备两条 outbox，令第一条失败并设置未来的 retry-after；再次扫描时断言第二条不发送。同时验证其他会话不受阻塞。

## R6：恢复匹配没有持久化关联，也没有时间约束

位置：[recovery.py](../../src/codex_im/core/recovery.py)，70–81、110–123 行；[store.py](../../src/codex_im/core/store.py)，333–360 行。

缺少 `codex_turn_id` 时，`_find()` 只比较输入并跳过已经绑定的远端 turn，没有使用设计要求的创建时间；找到结果后也没有把这个 Codex turn ID 写回本地记录，或修正 thread 的 materialized 状态。

具体路径：任务 A 在接受请求后、记录 ID 前崩溃，恢复时按输入找到结果；A 的远端 ID 仍未被绑定。之后用户再次发送相同输入，任务 B 在真正提交前崩溃，恢复就可能把 A 的旧结果当成 B 的完成结果。B 没执行却被标记 completed，不能再通过 `/retry` 找回。另一个后果是实际执行过的 thread 仍可能被当作 created/0-turn 而静默替换。

建议：对候选 turn 增加时间和唯一性约束；匹配成功后原子地保存远端 ID 并修正 thread 状态。不明确的匹配保持 unknown。修正过程不能重复增加 turn_count。

Ubuntu 回归：先完成一次“无 ID 的成功恢复”，随后用完全相同的输入制造“提交前崩溃”，断言第二次不会收到旧结果；检查第一条记录的远端 ID 已保存。

## R7：恢复会遗漏尚未投递的 async 提问

位置：[recovery.py](../../src/codex_im/core/recovery.py)，114–123 行；[events.py](../../src/codex_im/codex/events.py)，`pick_final_text()`；[sessions.py](../../src/codex_im/core/sessions.py)，487–492 行。

正常路径为 async agentMessage 建立问题状态和独立 outbox；恢复路径仅调用 `pick_final_text()`，而这个函数特意排除了 async 消息。如果 Codex 已保存问题，但 bridge 在写入该问题的 outbox 前崩溃，恢复不会补发。只有问题、没有普通最终回答的 turn 会被补发成“已完成，没有文字回复”。

建议：恢复按 item 扫描需要独立投递的消息，以稳定的 `(thread, turn, item)` 身份去重补入 outbox，同时恢复问题状态；不能只依赖最后的 final text。

Ubuntu 回归：历史中放入一个 completed turn，含 async 问题而本地没有相应 outbox；检查问题被补发且重复恢复不会重复建记录。另覆盖仍在运行的历史。

## R8：Email 引用链会产生新的会话键

位置：[mail/parse.py](../../src/codex_im/platforms/mail/parse.py)，35–43 行；[mail/adapter.py](../../src/codex_im/platforms/mail/adapter.py)，180–193、208–221 行。

`thread_root()` 把 In-Reply-To 的直接父 ID 当作根，没有查询“消息 ID → 既有会话”的映射。机器人回复生成新的 Message-ID 后，若下一封消息只有 `In-Reply-To: <机器人回复 ID>`，会话键就从原始邮件 ID 变成机器人回复 ID，导致创建新的 Codex 上下文。

即使邮件始终带 References，`(references + [message_id])[-20:]` 也会在链增长后移除最早的根 ID；下一封回复再取 `references[0]`，仍然会切换会话。

建议：持久化收到和发出的邮件 Message-ID 到稳定会话根的映射，沿已知父消息解析；截断 References 时保留根 ID。测试应从机器人实际构造的回复头继续生成下一封入站邮件。

Ubuntu 回归：分别覆盖“只有 In-Reply-To 的回复”和超过 20 个引用 ID 的往返，断言仍使用原 session_key/thread_id。

## R9：首次登录和 smoke 没有出网代理依赖

位置：[Makefile](../../Makefile)，27–31 行；[compose.yaml](../../deploy/compose.yaml)，16–38、57–66 行。

文档顺序是 build → login → smoke → up。`make login` 只 run agent，`make smoke` 只 run bridge 及其 agent 依赖。两者都没有启动 egress-proxy，agent 服务也未声明该依赖。

在首次安装且尚未运行服务时，agent 位于 internal 网络，唯一指定的出网代理不存在，登录和模型请求无法按这个顺序完成。这是命令和服务依赖的静态缺口，与 squid 版本是否接受配置是两件事。

建议：为代理添加正确的服务依赖和就绪等待，或让 login/smoke 目标显式准备所需服务。避免为解决这个问题取消 agent 的网络隔离。

Ubuntu 回归：在没有任何现存 codex-im 服务的环境中，严格按 README 的首次安装顺序验证。

## 其他明确的功能缺口

### R10：只有 final 类型做了分段（P2）

位置：[outbox.py](../../src/codex_im/core/outbox.py)，38–52 行；[finalize.py](../../src/codex_im/core/finalize.py)，73–81 行；[telegram/adapter.py](../../src/codex_im/platforms/telegram/adapter.py)，46–54、194–210 行。

`notice()` 和 `async_question()` 都把全文放入单条 outbox。超过 Telegram 长度上限的 async 问题会得到 BadRequest，并作为永久失败变成 dead。需要让所有出站文本经过统一的长度处理，同时为分段后的提问保留稳定去重身份和顺序。Ubuntu 上补充超长 async 问题的回归测试。

### R11：停止操作不关闭问题状态（P2）

位置：[sessions.py](../../src/codex_im/core/sessions.py)，554–571 行；[store.py](../../src/codex_im/core/store.py)，468–473 行。

`close_open_questions()` 只在成功 steer 和开始下一轮时调用。运行中或空闲时 `/stop` 都不会关闭问题，因此 `/status` 仍显示待回答数量，与 V1-4 的期望不符。停止应关闭当前 thread 的未完成问题；补充“问题发出后停止”的测试，而不只测试 turn 被中断。

### R12：群聊命令绕过 mention 检查（P2）

位置：[router.py](../../src/codex_im/core/router.py)，50–53 行。

条件 `msg.is_group and not msg.mentions_bot and command is None` 仅拦截未 @ 的普通消息。白名单用户在群里发裸 `/stop` 或 `/new`，即使没有指定本机器人，也会改变当前 Codex 会话。D9 和平台验收清单没有规定命令例外。需要落实统一的定向规则，或先把例外明确写进设计；给“未 @ 的群命令”增加测试。

## 测试覆盖方面的结论

现有测试是有用的正常路径基础，但不能据此认为 V1–V7 的所有子场景均已覆盖：

- FakeTurnHandle.interrupt() 总是立即产生 interrupted 终态，缺少拒绝中断、不返回 RPC、远端继续运行的替身。
- steer() 总是成功，缺少“远端已接收，本地没有得到确认”的替身。
- V5 测试只有 `/new` 加后续消息，没有 `/stop` → `/new` → 后续消息的完整顺序。
- 投递重试只有一条结果，没有同会话多条结果的退避顺序。
- 恢复历史缺少创建时间、async 问题、重复文本、多次崩溃及已恢复 ID 的唯一性检查。
- Email 往返测试使用固定 References，没有覆盖仅有父 ID 和引用链截断。

建议先补 R1–R4 的执行与控制不变量，再修复恢复及投递问题。对应测试都应在 Ubuntu 执行并记录结果；本次没有新增或运行测试。
